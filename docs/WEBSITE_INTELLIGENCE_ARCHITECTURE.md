# Website Intelligence — Architecture

Documents what is actually implemented (Phases 1–9 of
`docs/superpowers/specs/2026-10-30-website-intelligence-design.md`), not planned future work.
Cross-references the existing numbered architecture docs rather than restating them.

## 1. Where this sits in the existing system

Website Intelligence is a new module alongside the existing acquisition/pipeline/document
layers documented in `06_SYSTEM_ARCHITECTURE.md` and `07_DATA_MODEL.md`. It deliberately does
**not** duplicate:

- SSRF protection → reuses `chanakya.security.validate_url`/`host_allowed` (see
  `13_SECURITY_AND_COMPLIANCE.md`).
- Document parsing (PDF/DOCX/XLSX/HTML, OCR fallback) → reuses `chanakya.documents`
  (see `09_DOCUMENT_PROCESSING.md`).
- Capability matching → reuses `chanakya.pipeline.classify.RuleClassifier` and the Wayam
  capability book (see `10_AI_MATCHING_AND_SCORING.md`).

It is distinct from `chanakya.acquisition` (the 9-provider job-manager platform for known
capability-driven fetches) and `chanakya.connectors` (GePNIC/CPPP-specific parsers) — Website
Intelligence crawls an **arbitrary, user-added** URL within an explicit same-origin scope,
which neither of those existing layers was built for.

## 2. New package: `chanakya.webcrawl`

| Module | Responsibility |
|---|---|
| `crawler.py` | Core crawl loop: robots.txt, sitemap discovery, same-origin link discovery, page/depth limits, document-link discovery, page text/title capture. SSRF-gated via `security.validate_url`. |
| `documents.py` | Downloads one document link, saves it, extracts text via `chanakya.documents.extract_document`. |
| `tender_extraction.py` | Deterministic, regex/label-anchored extraction of government-tender fields (tender ID, organisation, dates, EMD, tender fee, state, opportunity type), each value paired with its source excerpt. |
| `company_extraction.py` | The company-website analogue: company name (from `<title>`), industries, technology capabilities, certifications, locations, contact email/phone. |
| `capability_matching.py` | Builds a minimal `TenderRecord` from extracted fields and classifies it through the real `pipeline.classify.RuleClassifier` — no second matching engine. |
| `export.py` | CSV/XLSX export of extracted tenders, preserving source URL and per-field excerpts. |
| `runner.py` | Orchestrates one `WebsiteCrawlJob`: runs the crawler, downloads/extracts documents, branches to tender-or-company extraction by `Website.category`, persists everything, updates job counters/status. |

## 3. Data model (new tables, additive to `07_DATA_MODEL.md`)

- **`websites`** — user-added site: name, base URL, category (closed set — see
  `GOVERNMENT_CRAWLER_USER_GUIDE.md`), description, enabled, crawl_config (JSON: max_pages,
  max_depth, extra_allowed_domains), last_crawl_at/status.
- **`website_crawl_jobs`** — one crawl run: status (`queued|running|paused|succeeded|partial|
  failed|cancelled`), page/document/tender counters, `cancel_requested`/`pause_requested` flags.
- **`website_pages`** — one row per discovered URL per crawl job: status
  (`fetched|failed|skipped_robots|skipped_offsite`), HTTP status, content type,
  `extracted_text`.
- **`website_documents`** — one row per downloaded PDF/DOC/DOCX: local path, sha256, extraction
  status, extracted text, source page URL.
- **`website_tenders`** — one row per page/document with at least one extracted tender field:
  `fields` (JSON: `{name: {value, excerpt, method}}`), `matches` (JSON: top capability hits).
- **`website_company_profiles`** — the company-website analogue of `website_tenders`, same
  evidence-per-field shape, no `matches` column (company profiles aren't capability-scored).

Every table follows this repo's existing conventions: `String(length)` helper, naive-UTC
`DateTime` via `now_utc()`, Alembic migrations autogenerated and hand-verified (see
`migrations/versions/` — every table/column here has its own revision, matching the existing
`AcquisitionJob` precedent).

## 4. Request flow (as actually implemented)

1. `POST /api/websites` → create a `Website` row.
2. `POST /api/websites/{id}/crawl-jobs` → create a `WebsiteCrawlJob` row, status `queued`.
3. `POST /api/websites/{id}/crawl-jobs/{job_id}/start` → **synchronously, within the request**,
   calls `webcrawl.runner.run_crawl_job`, which:
   - Validates/crawls same-origin pages (`crawl_website`), respecting robots.txt/sitemap/
     page+depth limits and a `should_stop` callback that re-reads `cancel_requested` from the
     database before each URL.
   - Downloads and extracts linked documents.
   - Branches on `Website.category`: tender extraction + capability matching for everything
     except `company_website`, which gets company-fact extraction instead.
   - Persists all `WebsitePage`/`WebsiteDocument`/`WebsiteTender`-or-`WebsiteCompanyProfile`
     rows and updates the job's final status/counters.
4. `GET .../pages`, `.../documents`, `.../tenders`, `.../company-profile` — read endpoints for
   the frontend's crawl-monitor view.
5. `GET .../tenders/export?format=csv|xlsx` — CSV/XLSX export.
6. `POST .../cancel`, `.../pause`, `.../resume` — flip status/flag columns; observed by the
   `should_stop` callback mid-crawl (cancel/pause), or re-enable continuation (resume is
   currently a status flip only — see Known Limitations below).

## 5. Known architectural limitation (documented shortcut)

`start_crawl_job` runs the crawl **synchronously inside the HTTP request** — there is no
background job executor for Website Intelligence crawls yet, unlike
`chanakya.acquisition.job_manager.JobManager`'s thread-pool model for provider jobs. This is
fine for the bounded page counts this phase targets (tens to low hundreds of pages) but will
need a `Container Apps Jobs`-style executor (see `COST_ESTIMATION_REPORT.md` §D.1) before crawl
sizes grow past what a single request's timeout budget tolerates. The `WebsiteCrawlJob` model
(status, `cancel_requested`/`pause_requested`) is already shaped for that upgrade — nothing in
the schema needs to change, only the execution path.

## 6. Frontend

`web/src/app/websites/` (list + detail pages), `web/src/lib/api-websites.ts` (typed client),
one new nav entry in `web/src/components/layout/shell.tsx`. Follows the existing
`components/ui.tsx` design system (`Panel`, `Button`, `StatusChip`, `EmptyState`) — no new UI
library or design tokens introduced.
